# Kiro History - Daily News Widget Development

## 2026-03-03 - Initial Development Session

### Project Overview
Built "Inference News" - a macOS widget for aggregating LLM inference optimization news from 12 sources.

### Key Features Implemented
1. **Async Collection with Progress Tracking**
   - Non-blocking article collection using QThread
   - Real-time progress updates showing source name and article count
   - Progress bar (0-100%) during collection
   - Final summary: "Done! X new articles"

2. **Data Sources (12 total)**
   - arXiv (cs.LG, cs.AI, cs.CL categories)
   - RSS Feeds (9): Hugging Face, PyTorch, vLLM, Google AI, OpenAI, Microsoft AI, SemiAnalysis, Together.ai, NVIDIA Developer
   - Anthropic (2): Research and Engineering blogs

3. **UI/UX**
   - Frameless, translucent window with rounded corners
   - Expand/collapse toggle (⤢/⤡) between 550×850px and 400×500px
   - Source filter dropdown (250px button, 300px list)
   - Auto-initialize database on first run
   - Draggable, resizable window
   - Minimize button for window management
   - Entire article card clickable to open URL
   - Hover effect on article cards

4. **Gemini Integration**
   - ✨ button on each article for AI summarization
   - Copies prompt to clipboard and opens Gemini web app
   - Simplified prompt: "Summarize this article: [title] [url]"
   - Dark tooltips with proper styling via QPalette

5. **Visual Indicators**
   - 🔥 icon for new articles (not yet viewed)
   - ✨ icon for Gemini summarization
   - Dark theme with rgba(28, 28, 30, 0.95) background

6. **Technical Solutions**
   - **Anthropic Date Extraction**: Used sitemap.xml to get accurate publication dates (avoiding JS-rendered page issues)
   - **Relevance Scoring**: Keyword-based filtering for most sources, no filtering for SemiAnalysis, Microsoft AI, vLLM, Together.ai, NVIDIA
   - **Database**: SQLite with auto-cleanup (180 days retention)
   - **Event Handling**: Proper event propagation for clickable cards with separate Gemini button

### Architecture
- **Widget**: PyQt5-based standalone app
- **Collectors**: Modular collectors for each source type (arXiv, RSS, web scraping)
- **Database**: SQLite with Article model (title, url, source, date, summary, relevance_score, tags)
- **Config**: YAML-based configuration for sources and keywords

### Deployment
- macOS app bundle with embedded Python environment
- Installed in /Applications/
- Launch script activates venv and runs widget.py

### Scope widened
From inference-optimization-only to the full stack: model architecture and
algorithms, training and scaling, post-training, inference optimization, serving
systems and engines, systems-level work, and AI chips.
- arXiv categories += cs.AR, cs.DC, cs.PF; query_terms rewritten as a broad
  40-term retrieval net (retrieval, NOT relevance); max_results 50 -> 100.
- Tag taxonomy rewritten: architecture, training, post-training, inference,
  serving, systems, hardware, quantization, attention, compression,
  optimization, multimodal, benchmarks, llm.
- Added a tag filter to the UI.

### Keyword filtering removed; Gemini used efficiently instead
Keyword matching was a bad relevance signal. Every candidate now goes to the
model. Affordable because of three things:
1. BATCHING - one request carries 20 articles and returns one verdict each,
   keyed by an echoed id. ~330 single calls per run becomes ~17. Out-of-order
   ids, missing entries and wrapped arrays are all handled; gaps fall back
   per-item rather than discarding the batch.
2. Dedup before classify - stored URLs are never re-sent.
3. data/rejected.json - a rejection ledger, so the ~90 off-topic stories in a
   HackerNews top-100 are judged ONCE, not 3x/day forever.
   Subtlety: only *model* rejections are recorded. A keyword-scored rejection is
   a low-confidence guess made while the API was unavailable, so recording it
   would permanently block a real verdict later. classify_many therefore returns
   (score, tags, judged_by) and pipeline.commit checks judged_by.
Feeds that are wholly on-topic set filter: false - still classified for tags,
never dropped on score.
Collectors refactored to two-phase (gather candidates -> batch classify ->
store) via the new collectors/pipeline.py. HackerNews keyword prefilter deleted.

### Gemini API notes (it moved under us)
- gemini-2.0-flash is RETIRED. Default is now gemini-3.5-flash-lite.
- generateContent is NOT deprecated ("remains fully supported") and is the
  default here; it was the only surface that reliably returned 200.
- The Interactions API works at /v1beta/interactions with gemini-3.6-flash and
  gemini-3.8-flash. The migration guide's /v1beta2/interactions is WRONG - 404
  with an empty body on every model.
- max_output_tokens INCLUDES thought tokens, and Gemini 3 thinks by default
  (floor is thinking_level minimal/low, never off). A 200-token cap truncated
  the JSON mid-object; budget is now 2048 + 120/article.
- responseSchema must be supplied or the model invents key names (it returned
  is_relevant instead of relevant). generateContent wants UPPER-case type names.
- The larger models frequently 503 "high demand" on the free tier; flash-lite
  does not. Transient 5xx now retries 3x with backoff.
- Free-tier RPM/RPD are no longer published per model; they are per-project in
  AI Studio. verify_gemini.py probes what a given key actually supports.

## 2026-09-23 (night) - Dashboard scrapped; rebuilt as a single briefing page

### The critique that caused this
"What's the point of knowing which keyword hit how many frequencies or momentum
or volume or source count? I want to know what are the key news I must look
into." Correct: volume/week, topic momentum, source mix and KPI counts are
analytics about the PIPELINE, not about the news. They prove the collector is
alive; they do not tell you what to read. Also: feed and pulse should not be
separate pages.

### What replaced it
DELETED site/pulse.html, site/pulse.js, all chart code, the KPI tiles, the viz
colour tokens and the dataviz palette work. One page now:
- "Start here": the 5 highest-importance items across all areas.
- One section per area of interest (fixed order), 6 items each, expandable.
- Every item shows a one-line justification of what is new and why it matters -
  that line is the product; it lets you skip without opening.
- An importance BAR (only-what-matters / worth-a-look / everything) instead of a
  sort order, because the question is what to read, not how to rank.

### Data model change
The classifier's single batched call now returns area + importance + why in
addition to relevance and tags, and returns a Verdict namedtuple rather than a
tuple. This REPLACED the separate paper-ranking pass added earlier the same
evening (rank_many, RANK_SCHEMA_*, the innovation/innovation_why columns, the
--rank backfill): folding the five innovation criteria into the importance
rubric covers all sources, not just papers, and costs no extra requests.
- database.py: innovation/innovation_why -> area/importance/why
- AREAS: architecture, new-models, inference-methods, inference-engines,
  silicon, training, other. Exactly one per article so sections stay clean.
- Unrated rows (keyword-fallback only) store no importance at all and are never
  hidden by the bar - a row cannot fail a test it was never given.

## 2026-09-23 (late night) - Storage diet, area pinning, page review

### Storage: the repo WOULD have blown up
Measured before changing anything. data/articles.json was 933 KB for 1383 rows
(691 B each), and the field breakdown was damning:
  summary          514 KB  55.1%   <- never rendered by the page
  title            101 KB  10.8%
  url               94 KB  10.1%
  published_date    49 KB   5.2%
  tags              33 KB   3.6%
  source            30 KB   3.2%
  relevance_score   26 KB   2.8%   <- superseded by importance
Rewritten 3x/day, that trends to ~15 MB as a single file within a year.
Fixes:
1. summary is now stored ONLY while a row is unrated (it is an input to
   classification, not output; reclassify.py still needs it until the row is
   judged). relevance_score dropped entirely. 691 -> 443 B per row.
2. Rolling hot window + monthly archives. data/articles.json keeps only the last
   ROOFLINE_HOT_DAYS (120) days - all the page can show - and older rows move to
   data/archive/YYYY-MM.json, written only when that month changes. The file the
   job rewrites 3x/day is therefore BOUNDED (~3 MB steady state) instead of
   growing forever, and archives are near-static in git. Only the hot file is
   published to Pages.
   store.hydrate() reads hot + all archives, so dedup still sees everything.

### Area assignment without asking the model blind
- Papers: title + abstract only, abstract truncated to 400 chars. Already the
  case; now documented.
- Feeds with a single beat: pinned in config.yaml (SemiAnalysis, Chips and Cheese
  -> silicon; vLLM Blog -> inference-engines; Interconnects -> training). The pin
  only fills in when the model says "other", so an off-beat post still lands
  right.
- HackerNews, the tricky one: a bare title with no abstract. The QUERY that
  surfaced the story is the evidence. Queries are now grouped by area in
  config.yaml (43 queries across 6 areas) and a hit inherits its group's area,
  overriding the model there. See pipeline.pick_area().

### Workflow correctness under the new layout
The race handler used to `git reset --hard` then merge only the hot file - which
would have DROPPED any row that aged into an archive during the losing run. Now
it re-derives through the store (merge_into_store.py): hydrate remote hot +
remote archives, add this run's rows, re-dump. Simulated a race with a stale
remote missing 40 rows and zero archives: 763 + 40 = 803 recovered, nothing
invented.

### Page review, prompted by "dashboard does not show tags for areas anymore"
Correct catch, and it was an oversight rather than a decision. Tag chips are back
on every item - the section header carries the area, so the chips are the finer
grain that helps scanning WITHIN a section. Also:
- Last updated now shows an absolute date and time ("updated 23 Sept 2026,
  22:17"), plus a footer line naming the window and total collected. It used to
  say "updated today", which is useless for spotting a stalled job.
- Dropped the "All time" range option: with a 120-day hot file it would have been
  a lie.
- Filters are now URL-addressable (?window=7&bar=0.6&q=vllm&unread=1), which makes
  views shareable and, more importantly, testable.
- The lede is suppressed when there are few results, since it would otherwise
  swallow the whole page and hide the area grouping.

### Verifying the dropdowns (they do work)
First measurement said they did not: identical item counts across every filter
state. That was the MEASUREMENT being wrong - the selector class="item[^"]*"
also matched item-body, item-title, item-why, item-meta, item-source. Counting
only `<a class="item` showed the truth: card count is pinned at 47 by design
(5 lede + 7 areas x 6) while the "Show N more" counts move correctly with the
filters - bar=0.6 collapses each area, window=90 expands it.

## 2026-09-23 (last) - Self-review of the populated briefing

Reviewed the live page now that 601 of 849 rows are rated, and MEASURED the
weaknesses rather than guessing at them:

1. Could not see WHERE things happened without scrolling. Fixed with area pills
   (not a dropdown, as asked): one click per front, keys 0-6, each pill carrying
   its count and a "+N" of items newer than the last visit. That +N is the actual
   catch-up signal - it answers "which fronts moved" at a glance.
2. "NEW" was on 100% of rows because it meant "unread", which carries no
   information on a page you have never marked. It now means "published since your
   last visit" (localStorage timestamp).
3. MEASURED: 31% of why-lines restated the title (title/why similarity >0.5 in
   187 of 601). e.g. "Topology-Stratified Materials Discovery with A Flow-Based
   Generative Model" -> "Uses topology-stratified flow-based generative models to
   improve crystal structure discovery." Zero added information. The prompt now
   forbids paraphrase explicitly ("if your sentence would still make sense as a
   subtitle, it is wrong") and demands the concrete delta versus prior work.
4. No synthesis: catching up on a front still meant reading three headlines and
   assembling the picture yourself. Added build_digest.py - one or two sentences
   per area per run, shown when a single front is selected. This is the highest-
   value feature for multi-front catch-up and costs ~6 requests.
5. MUST READ over-fired (3 of 3 in architecture) because scores cluster. The
   threshold is now the top decile OF WHAT IS ON SCREEN, recomputed per view,
   rather than an absolute 0.75.

MEASURED and dropped: duplicate-story clustering. Only 2 near-duplicate title
groups across 849 rows, so the same-story-from-three-sources problem I expected
does not exist at this volume. Not worth building.

Known remaining weaknesses (named, not fixed):
- Area errors are visible: agent-tooling papers land in "architecture", and a
  materials-science paper was rated in-scope at all. The areas/rubric need
  tightening, which is a prompt change rather than a layout one.
- Read state is per-browser localStorage, so it does not follow you across
  devices. Fixing that needs a backend, which the whole design exists to avoid.

## 2026-09-23 (postscript) - Two operational bugs, both mine

### "803 of 849 items are not classified yet" - a STALE CACHE, not lost data
Reported after a backfill. Checked all four copies:
  local working tree  849 rows, 655 rated
  local HEAD          849 rows, 655 rated
  origin/main         849 rows, 653 rated
  live site           849 rows, 653 rated
Nothing was lost. The browser was serving a cached data/articles.json from before
the backfill. The page fetched it with default caching, so a file that changes
3x/day could be served hours stale - and the failure mode looked exactly like the
backfill having been discarded, which is the worst kind of bug. Both fetches now
pass {cache: "no-cache"} to force revalidation.

### Repeated push rejections - now handled by ./sync.sh
The scheduled job commits to main three times a day, so a manual push after a
local backfill races it. Worse, the obvious resolutions are both wrong: taking
the remote's copy discards the ratings, and taking ours discards newly collected
rows. sync.sh runs reclassify (optionally build_digest), then merges by
re-deriving through merge_into_store.py - which adds the rows only the remote has
AND enriches the rows whose ratings only we have - and retries the push up to
three times. The manual loop is now one command instead of a git puzzle.

Note to self: I had been running merge/push cycles in the same working tree the

## 2026-09-23 (postscript 2) - "194 items not classified" was a THIRD state I forgot

### The bug
The notice kept reporting ~194 unclassified rows after repeated backfills.
Inspected them: every single one had tags='' and area='other', which is the
signature of the model having judged them and returned relevant: false. Samples
confirmed it - "Fully Discrete Multi-Entropy Stability of High-Order Schemes for
Compressible MHD", "The Price of Intelligence Is Falling Rapidly" - correctly
off-topic.

parse_verdicts set importance=None for an irrelevant item, which made
"judged and rejected" INDISTINGUISHABLE FROM "never judged". Three consequences,
all bad:
1. The page reported them as unclassified forever.
2. reclassify.py re-targeted all of them on every run - quota burned re-deciding
   the same rejections, indefinitely.
3. They accumulated in "Everything else" instead of being filtered out.

Fix: an irrelevant verdict now records importance 0.0. Zero is a judgement; None
means "ask again". reclassify writes 0.0 rather than None for the same reason, and
the notice threshold dropped from 20% to 5% now that it counts only genuinely
unjudged rows.

### Why they were stored at all
Two legitimate paths: rows collected before Gemini was wired up (keyword scoring
let them past min_score), and always_keep sources - SemiAnalysis, airealist,
Interconnects, Chips and Cheese are filter: false, so they are never dropped on
score by design. That accounts for 59 of the 194. Going forward, off-topic items
from filtered sources are rejected at collection time and never stored, so this
is one-time legacy cleanup, not a recurring condition.

### Still open
Whether off-topic rows should be stored at 0.0 at all, or deleted and added to the
rejection ledger. Deleting is cleaner for the always_keep=false sources but
contradicts filter: false for the others. Left stored and filtered for now, since
the importance bar already hides them.

## 2026-09-23 (postscript 3) - I was wrong: the scope had a hole, not the articles

Pushback: '"The Price of Intelligence Is Falling Rapidly" is not off-topic.'
Correct, and I had compounded the error by citing that rejection as EVIDENCE the
classifier was working. Checked whether it was systematic rather than a one-off,
and it plainly was - all of these had been rejected:
  The Price of Intelligence Is Falling Rapidly
  Tokens Too Cheap to Meter
  The Economics of Open-Weight Inference
  Claude Opus 5.5 Intelligence, Performance and Price Analysis
  The current balance of power in open models
  What is So Hard About Behind-The-Meter Power For Datacenters
  Korea's Trillion-Dollar Sovereign AI Investment: Nvidia Wins, Hynix Loses
22 SemiAnalysis and 11 Interconnects items were being dropped, which should have
been the tell much earlier: those sources were chosen deliberately and one of them
is MOSTLY economics.

Root cause: SCOPE listed architecture, training, inference, serving and chips -
and said nothing about cost. The model applied a too-narrow scope faithfully. I
had even raised "economics/capex: signal or noise?" as an open question earlier in
the session and then never resolved it, so this was a known gap left to rot.

Fixes:
- SCOPE now covers cost per token, inference pricing, hardware/memory supply, fab
  and accelerator availability, and datacenter capacity/power/grid interconnect,
  with explicit reasoning that falling cost per token is a headline OUTCOME of the
  stack and that power is the binding constraint on what can be run.
- SCOPE now also states what is OUT explicitly (discourse and hype with no
  technical/cost/capacity content, launches with no performance or price detail,
  safety and regulation debate, applications on top of models). Naming the
  exclusions is what keeps the widening from turning the feed into general AI news.
- New area: economics, "Cost & economics", between training and other. Keys 0-7.
- reclassify.py --rejected re-judges rows previously scored 0.0, which is the
  mechanism for recovering from a scope change like this one.

Lesson: when the classifier rejects content from a source that was deliberately
chosen for that content, suspect the scope before crediting the model.
